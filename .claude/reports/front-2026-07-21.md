## Lot 0 — Infra partagée (commit `22d517f`)

Fichiers créés :
- `apps/web/src/hooks/useAsyncData.ts` (85 lignes) — hook générique transverse. Signature :
  `useAsyncData<T>(fetchFn: () => Promise<T>, deps: DependencyList, options?: { fallbackErrorMessage?: string }): { data, isLoading, error, refetch }`.
  Protection anti-réponse-obsolète via un flag `isIgnored` posé dans le cleanup de l'effet : si `deps`
  change ou si le composant est démonté avant résolution de la promesse en cours, le résultat est ignoré.
  `fetchFn` est lu via une ref à chaque exécution de l'effet — l'appelant n'a pas besoin de la mémoïser
  avec `useCallback`. `refetch()` incrémente un `refetchToken` interne qui déclenche un rechargement
  explicite sans changer les dépendances.
- `apps/web/src/utils/apiError.ts` (86 lignes) — `getErrorMessage(error, fallback?)` et
  `getErrorStatus(error)`. Ordre de priorité du message retourné : 1) message métier backend
  (`response.data.message`) 2) message par code HTTP (401/403/404/409/400/422, table `STATUS_MESSAGES`)
  3) générique 5xx 4) générique réseau (si `error.request` sans `error.response`) 5) `fallback` fourni
  par l'appelant 6) message générique par défaut.
- `apps/web/src/test-helpers.tsx` (28 lignes) — utilitaires de test partagés introduits en support du lot.

## Écarts URL / docs/routes.md repérés en cours de chantier (signalés, non corrigés)

Ces écarts sont documentés dans le code source par un marqueur `ÉCART docs/routes.md` en commentaire
JSDoc, avec la mention explicite "comportement préexistant reproduit tel quel — ne pas corriger sans
arbitrage". Ils datent d'avant ce chantier ; le chantier les a rendus visibles/traçables en les
documentant au moment de la migration vers `src/api/`.

### `apps/web/src/api/finance.ts`
1. **`GET /finance-events`** (ligne ~146) — route non documentée pour aucun microservice dans
   `docs/routes.md`, ni sous `/finance/`, ni ailleurs.
2. **`PATCH /financial-settings/rewards`** (ligne ~158) — `docs/routes.md` documente
   `PATCH /finance/settings` (préfixe `/finance` + chemin `/settings`) pour finance-credit-service ;
   l'appel réel utilise un chemin et un préfixe différents.
3. **`GET /teacher-payment-requests`** (ligne ~170) — `docs/routes.md` documente
   `/finance/teacher-payment-requests` (préfixe `/finance` manquant dans l'appel réel).
4. **`POST /teacher-payment-requests`** (ligne ~182) — même écart de préfixe que le point 3.
5. **`POST /teacher-payment-requests/:id/validate`** (ligne ~195) — `docs/routes.md` documente
   `PATCH /finance/teacher-payment-requests/:id/status` : verbe HTTP (POST vs PATCH), chemin
   (`/validate` vs `/status`) et préfixe (`/finance` manquant) tous différents. C'est l'écart le plus
   significatif car il touche une action métier (validation d'une demande de paiement formateur par
   l'administrateur financier) — potentiel bug pré-existant côté contrat front/gateway/backend à
   investiguer séparément, hors périmètre de ce chantier de normalisation.

### `apps/web/src/api/teacherRequests.ts`
6. **`GET`/`PATCH /profiles/:teacherId/validation`** — utilisé par `TeacherValidationPanel.tsx`, non
   documenté dans `docs/routes.md` : seul `POST /profiles/:teacherId/ap-status` est documenté pour
   profile-service (promotion Formateur → Animateur Pédagogique). À vérifier si `validation` est une
   route réellement exposée côté profile-service ou un résidu d'une évolution non documentée.

Ces 6 écarts sont préexistants au chantier (comportement runtime non modifié) — ils ont simplement été
rendus visibles et traçables par la migration vers des modules `api/` centralisés et documentés.

Pour mémoire, un écart voisin mais différent — l'URL testée pour `PATCH /teacher-requests/:id/status`
contenait un doublon `requests/requests` dans un test — a été corrigé **avant** ce chantier, sur master,
par le commit `af1b244` (`fix(front): corriger l'URL testée pour PATCH .../status (teacher-requests) (#47)`).
Ce n'est pas un écart de ce chantier ; mentionné ici uniquement pour éviter toute confusion avec les
écarts finance ci-dessus.
