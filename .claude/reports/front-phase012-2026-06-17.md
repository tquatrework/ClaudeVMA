## Décisions techniques

1. **Module API unifié** : `contentCatalog.ts` supporte les réponses paginées (`data/meta`) et les tableaux directs pour rester compatible avec le contrat `/api/v1`.

2. **EvaluationAttemptPage** : implémente la machine d'état `not_started → in_progress → completed`. Le blocage de la solution est visuel (message explicite) pendant la phase `in_progress`, conformément à la règle métier de la spec.

3. **ContentValidationQueue** : les décisions de validation (approve/reject) sont gérées en optimistic update local. La route de validation n'étant pas spécifiée dans la phase 12, le composant délègue l'action via callback au parent. Quand la route `/contents/{id}/validate` sera disponible (phase future), le parent pourra l'appeler avant de retirer l'item.

4. **TutorialCatalogPage** : intègre `ContentCommentsPanel` directement dans la vue détail sans navigation supplémentaire pour éviter une page de détail tutoriel redondante (les tutoriels ne nécessitent pas de réponse ni de correction).

5. **ExerciseSolution via `POST /exercises/{id}/solutions`** : la solution est créée/mise à jour par le formateur depuis `ExerciseDetailPage`. En cas de 409 (solution existante), un message approprié est affiché.

## Limites restantes

| Limitation | Raison |
|---|---|
| Pas de `GET /exercises/:id` individuel | Route non spécifiée en phase 12 ; `ExerciseDetailPage` affiche l'id et les sections d'action sans recharger le contenu complet |
| Actions de validation non persistées côté API | Route `/contents/{id}/validate` ou équivalent absent de la spec phase 12 ; optimistic update local seulement |
| `POST /contents/{id}/ratings` exposé dans l'API mais sans UI dédiée | La notation est typiquement un bouton inline ; ajout prévu en enrichissement |
| Correction ouverte via learning-activity-service non intégrée | Périmètre phase 13 (learning-activity-service) ; mocké conformément à la spec `allowedMocksUntilDependenciesExist` |
