## Décisions techniques

### Architecture
- `AuthContext` centralise la session : stockage JWT en localStorage, intercepteur axios pour injection et gestion 401 automatique.
- `ProtectedRoute` prend un tableau optionnel `allowedRoles` : sans rôle → vérifie uniquement l'auth ; avec rôles → redirige vers `/forbidden` si non autorisé.
- Les appels API passent exclusivement par `apiClient` (axios instance pointant sur `VITE_API_BASE_URL`) — jamais vers les microservices directement.

### Règles métier frontend
- **FRONT-FB-001** : `NotebookPage` bloque `parent_financeur` avec `<Navigate to="/forbidden">` avant tout chargement. La route dans `App.tsx` ne liste pas non plus ce rôle dans `allowedRoles`.
- **FRONT-FB-002** : le lien visio dans `ActivityDetailPage` n'est affiché que si `videoRoomId` est présent dans la réponse API — le contrôle réel reste côté backend (`/video/rooms/:id/join` retourne 403 si non autorisé).
- **FRONT-FB-005** : aucun appel direct aux microservices — tout passe par `apiClient` → api-gateway.

### TypeScript
- `/// <reference types="vite/client" />` dans `api/client.ts` pour typer `import.meta.env`.
- `noUnusedLocals/Parameters` désactivés pour accepter les imports `React` (React 17+ new JSX transform, les imports sont techniques mais tolérés).
- 0 erreur TypeScript.

### Tests
- 3 tests vitest/testing-library couvrant `ProtectedRoute` : redirection non-auth, rendu auth OK, redirection rôle refusé. Tous passent.

### Dockerfile
- Stage 1 : `node:20-alpine` — `npm install` + `npm run build`
- Stage 2 : `nginx:alpine` — copie `dist/` + config SPA fallback (`try_files $uri /index.html`)
- `VITE_API_BASE_URL` injectée via `ARG`/`ENV` au build (valeur runtime via docker-compose env)

## Points en suspens

1. **Refresh token** : l'intercepteur 401 efface la session et redirige mais ne tente pas de rafraîchir automatiquement avec `refresh_token`. À implémenter si l'expiration courte du JWT devient gênante.
2. **Conversations** : la messagerie utilise `GET /messages` comme liste de conversations mais l'API `communication-service` expose `GET /messages/conversation/:id`. Le modèle de conversation (liste des interlocuteurs) dépend d'un contrat à préciser avec le service.
3. **Carnet personnel** : le scaffold appelle `/logs/student/:id?type=notebook` — à confirmer avec `pedagogical-log-service` si un type ou endpoint dédié est prévu.
4. **Profil edit** : seul le profil administratif est éditable depuis l'UI. L'édition du profil pédagogique (`PUT /profiles/:userId/pedagogical`) nécessite un second formulaire à ajouter.
5. **Pagination** : aucune pagination implémentée sur les listes (activités, demandes, logs). À prévoir dès que le volume de données croît.
6. **Gestion d'état globale** : l'état est local à chaque page (useState). Si des données partagées (notifications, profil courant) deviennent complexes, ajouter React Query ou Zustand.
